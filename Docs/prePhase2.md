# Phase2前レビープラン

今回のWails移行（通信層のネイティブ化）において、手戻りとバグのリスクを最小限に抑えるための「リファクタリングの要否判断の目安」と、要と判断された場合の「進め方の方針」をまとめました。
------------------------------
## 1. リファクタリングの要否判断の目安（チェックリスト）
通信層の書き換え（SSE ➔ Wails Events、AssetServer ➔ Goバインディング）に着手する前に、以下の5つの問いでコードを評価します。1つでも「No」がある場合は、ネイティブ化の前にリファクタリングが必要です。

## ▢ 目安1：フロントエンドの描画と通信が分離されているか？

* 確認ポイント: Reactなどの画面コンポーネントの中に、fetch、axios、new EventSource、あるいはWails固有の window.go... といった記述が直接書かれていないか。
* 判定基準: ✕（コンポーネント内に通信が混在 ➔ 要リファクタ）、◯（通信は api.ts や useEvent.ts などの専用モジュールに閉じている）。

## ▢ 目安2：GoのコアロジックがHTTPプロトコルに依存していないか？

* 確認ポイント: ファイル監視（Watcher）やPlantUMLの処理ロジックが、http.ResponseWriter や http.HandlerFunc といったWebサーバーの仕組みと直接結合していないか。
* 判定基準: ✕（コアロジックがHTTPの文脈でしか動かせない ➔ 要リファクタ）、◯（コアロジックはGoの channel やコールバックで動き、HTTPハンドラーはそれを外側でラップしているだけ）。

## ▢ 目安3：データ構造（型）が独立しているか？

* 確認ポイント: フロントエンドとGoの間でやり取りするデータの送受信形式（JSONのスキーマなど）が、通信経路（SSEかWailsか）に依存する形になっていないか。
* 判定基準: ✕（通信層を変えるとデータのパース処理まで壊れる ➔ 要リファクタ）、◯（データ構造は純粋なオブジェクト/構造体として定義されている）。

------------------------------
## 2. リファクタリングが必要（要）となったときの方針
リスク判定で「リファクタリングが必要」となった場合は、「既存の動く状態を壊さずに、結合度だけを下げる」ために以下の方針を徹底します。

## 方針①：通信の「窓口（インターフェース）」を一本化する

* フロントエンド:
通信処理をすべて隠蔽する「アダプター層（例: streamClient.ts）」を1つだけ作ります。画面側は「このアダプターからデータをもらう」という契約（インターフェース）に従うようにコードを書き換えます。内部がSSEのままでも、この一本化を先に行います。
* Go側:
ファイル変更などのイベント発生源と、それを配信する仕組みの間に channel を挟みます。「Watcher ➔ Channel ➔ SSEハンドラー」という構造にしておけば、後から「Watcher ➔ Channel ➔ Wails Events」への差し替えが容易になります。

## 方針②：「振る舞いを変えない」テストを担保する

* リファクタリングの前後で、アプリの挙動（ファイル保存時にブラウザがリロードされること）が変わっていないかをすぐに確認できる手順（手動のミニテスト、または自動テスト）を確立してからコードを触り始めます。

## 方針③：ネイティブ化のコードは1行も書かない

* このフェーズのゴールは「疎結合にすること」です。WailsのAPIを組み込む誘惑に駆られますが、まずは「SSEとAssetServerのままで、コードの配置と依存関係だけを綺麗に整理する」ことに徹します。

## 次のアクション
まずは、最もリスクが高いとされる「SSE（Live re-renderの通知層）」の周辺からチェックすることをおすすめします。
Go側の internal/watcher（またはそれに類するファイル監視処理）が、どのようにフロントエンドへの通知処理を呼び出しているか、現状の構造を思い出せる範囲で教えていただけますか？それに応じた具体的な切り離し手順を検討できます。
